# Windows 검증 기록

기준: Windows 10/11 x64 대상, .NET SDK 10.0.403, 기능 브랜치 `codex/windows-port`.

## 자동 검증

`scripts/build-windows.ps1 -Publish`는 다음 검사를 수행하며 실제 카카오톡에 메시지나 파일을 보내지 않습니다.

- Core: CSV/TSV·XLSX, 희소 셀·다중 시트·기존 통합 문서, UUID와 확장 필드, 원자적 백업, Mac ISO 날짜, 프리셋, 첨부 매칭 및 발송 검증.
- Automation: 드라이런의 전송 함수 미호출, 고정된 검토 사본, 개별→공통→파일 순서, 단일·다중·첨부 단독 발송, 중단·부분 실패·영속 기록과 재전송 차단. 실제 전송은 가상 연결로 검증합니다.
- WPF smoke: 합성 학생 데이터만 사용한 6개 화면, 입력·미리보기, 붙여넣기·되돌리기, 모의고사 집계, 초안·백업 복원, 발송 식별자 보호와 단일 인스턴스.

현재 소스의 콘솔 회귀 검사는 Core 23개, Automation 65개입니다. 마지막 로컬 Automation 통과 기록은 54/54이며, 후속 모달·소유권·마지막 입력 검사 회귀 사례는 Windows 실행 정책 차단으로 로컬 재실행하지 못했습니다. 커밋 `cdaf5f4`의 별도 [GitHub Windows CI](https://github.com/SleepingDawn/notice-sender-mac/actions/runs/41660088595)에서 빌드, 전체 콘솔 회귀 검사, WPF smoke, 자체 포함 배포본 생성이 모두 통과했습니다. WPF smoke는 별도 프로세스의 종료 코드로 검사합니다. 이전 3.1.1 배포 ZIP은 압축 해제 후 자체 포함 실행 smoke도 통과했습니다. 새 미리보기 빌드의 CI/로컬 검증 범위는 구분해서 기록합니다.

## 실제 카카오톡 검사 (2026-11-03)

사용자는 기존 로그인 계정의 방으로 드라이런을 먼저 수행하고, 실제 전송은 확인된 챗봇 방에서만 수행하도록 승인했습니다. 학생·지인 방으로 실제 전송하지 않았습니다. 합성 문구와 합성 임시 파일만 테스트 대상으로 준비했습니다.

검사 보고서는 개인정보가 섞일 수 있으므로 Git에 포함하지 않는 `outputs/`에 보관합니다. 성공한 드라이런은 `windows-live-20261103-223620.json`, 실제 전송 차단 기록은 `windows-live-20261103-224529.json`입니다. 제한된 실행 환경의 `EnumWindows failed`는 대화형 데스크톱 접근 차이로 재현·분리했습니다. 앱은 동일 사용자로 실행한 카카오톡 창을 읽을 수 있어야 합니다.

이후 물리 Esc 입력으로 Computer Use가 중단되어 추가 카카오톡 조작을 중지했습니다. 실제 메시지 또는 파일 전송 성공으로 보고하지 않습니다. `전송 요청 완료` 또한 서버 수신·읽음 보장을 뜻하지 않습니다.

## 후속 실제 검증 순서

### 2026-11-04 로컬 검증 범위 재확인

서명 대기 중에도 모든 로컬 검증이 차단되는 것은 아닙니다. 카카오톡 자동화 모듈을 참조하지 않는 `NoticeSender.Core.Tests`를 기존 SDK의 원래 `dotnet run --project Windows/NoticeSender.Core.Tests --configuration Release --no-restore` 경로로 실행하여 **23/23 통과**를 확인했습니다. CSV·EUC-KR·다중 시트 XLSX, 학생/반/프리셋·백업 호환, 공지 생성, 첨부파일 매칭과 발송 계획·불확실 항목 재시도 방지의 데이터 처리를 검사합니다. 서명 감사 스크립트 검사도 **8/8 통과**했습니다.

이는 실제 카카오톡 입력·업로드·전송 성공을 의미하지 않습니다. 확인한 CodeIntegrity 차단은 `NoticeSender.Automation` 및 해당 시험 구성요소에 있으며 이를 다시 실행하거나 다른 호스트로 옮겨 실행하지 않았습니다. 보호 설정을 바꾸지 않았고 실제 학생 DB를 사용하거나 메시지·파일을 보내지 않았습니다. 로컬 증거 요약은 비공개 `outputs/windows-local-validation-20261104.json`에 기록합니다.

### 앱 자체 방 열기 시험 추가 기록

3.1.1 개발 중 첫 앱 시험은 기존 창 1개 확인 후 다음 방 열기에 실패했습니다(`outputs/top-five-app-dry-run-1.json`, 종료1). 이후 사용자가 계속 진행하도록 요청하여, 수동 방 열기 없이 실제 앱으로 반복 재현·수정했습니다. `조용한 채팅방` 묶음은 제외했습니다.

활성 결과 목록에만 열기 확인을 보내고, 비동기 검색 갱신 중에는 같은 목록의 확인만 최대 두 번 추가하도록 수정했습니다. 각 시도는 같은 검색어·PID·소유 관계·취소 상태를 다시 검사합니다. 열기 성공은 정확히 일치하는 고유한 네이티브 방 제목으로 확인합니다. 마지막 실제 앱 보고서 `outputs/top-five-app-dry-run-5.json`은 2026-11-03 23:27 KST, **5/5 성공, 종료0**입니다. 마지막 방은 이 실행에서 새로 열었고, 다른 네 방도 앞선 실제 앱 실행에 새로 연 증거가 있습니다. 초기 Computer Use 직접 클릭은 이 증거에 포함하지 않습니다. 메시지·파일 기능은 호출하지 않았습니다.

### 실제 봇 시험 및 로컬 실행 차단

`--bot-send-test --room EXACT --acknowledge-bot-only --capture-bot-evidence`는 별도의 가상 DB와 합성 자료로 7개 사례를 준비합니다. 실제 대상은 엄격한 봇 허용 목록으로 제한하고, 처음 검증한 PID·방 HWND·입력창 HWND를 시험 전체에서 고정합니다. 테스트 문구·생성 파일 이외의 전송은 차단합니다. PNG는 정확히 검증한 봇 창과 같은 프로세스의 소유 창에 대한 진단 자료이며, 위치 선택·OCR 제어·전송 성공 판정에 사용하지 않습니다.

첫 실제 봇 실행 `outputs/bot-app-send-1.json`은 입력 전에 중지됐습니다. 캡처로 상시 채널 메뉴가 모달이 아님을 확인해 분류를 수정했습니다. 새 DLL 실행은 Windows CodeIntegrity 이벤트3077, 정책 `{0283ac0f-fff1-49ae-ada1-8a933130cad6}`(Smart App Control)와 0x800711C7 오류로 차단됐습니다. 디버그의 정상 재시도에서도 재현되어 추가 로컬 실행을 중지했습니다. 보안 설정을 바꾸거나 다른 이름·경로·호스트로 실행하지 않았습니다. 사용자에게 서명 수단과 별도 Windows 환경이 없음을 확인했습니다.

기존 GitHub Windows CI는 정상 사용 가능합니다. CI는 실제 카카오톡 계정으로 보내지 않으며, 이 PC의 실전송 검증을 대체하지 않습니다. 현재 텍스트·단일/다중 파일·PDF·이미지·실제 부분 전송 중단은 여전히 **미검증**입니다. 정상적인 서명 또는 실행이 허용된 Windows 시험 환경이 마련되면 아래 실제 순서를 재개합니다.

## 로컬 VM 후속 검증 (2026-11-04)

호스트 보호 설정은 변경하지 않았습니다. 사용자가 설치·로그인한 전용 Windows VM에서 일반 대화형 계정으로 실행했고, 실제 전송 대상은 확인한 `카카오톡 선물하기` 봇 하나입니다. 학생 DB는 복사하지 않았습니다. 앞의 11월3일 표는 당시 기록이며 이후 결과는 아래와 같습니다.

| 사례 | 실제 관찰 | 통합 앱의 완료 판정 |
| --- | --- | --- |
| A: 개별 + 공통 5개 | 앱이 6개 문구를 순서대로 전송, 봇 응답 확인 | 통과 |
| B: 텍스트 + TXT | 초기 별도 확인 도구와 후속 앱 자체 확인에서 각각 도착 확인 | 확인 필요 |
| C: 텍스트 + TXT/CSV | 별도 확인 도구 및 후속 앱 자체 확인에서 두 파일 도착 확인 | 확인 필요 |
| D: 파일만 전송 | 초기 별도 확인 도구와 후속 앱 자체 확인에서 각각 도착 확인 | 확인 필요 |

| E-PNG | 별도 확인 도구 및 후속 앱 자체 확인에서 고유 시험 문구가 있는 이미지 말풍선 확인 | 확인 필요 |

전체 7개 사례의 실제 효과를 여러 독립 실행에서 관찰한 결과이며, 앱 전체 자동 시험 7/7 통과를 뜻하지 않습니다. 불확실한 보고서는 원래 상태로 보존했고 동일 항목을 자동 재전송하지 않았습니다.

앱 자체 합성 첨부 확인은 `--confirm-native-bot-files`로만 켜집니다. `--acknowledge-bot-only`, `--capture-bot-evidence`와 하나의 첨부 단계(`--step B|C|D|E-PDF|E-PNG`)가 함께 필요합니다. 지원하는 카카오톡 실행 파일의 정확한 버전·해시, 합성 파일명과 전체 원본 바이트, 봇/PID/창/입력창 소유권, 새 확인 창의 컨트롤 구조와 포커스를 재검사합니다. 파일 확인 직전 화면과 파일 해시 기록을 남기지 못하면 전송하지 않습니다. 한 번의 확인 시도를 소비하면 재시도하지 않으며, 대화상자 소멸만으로 완료를 표시하지 않습니다. 이 옵션은 일반 학생 발송 경로를 변경하지 않습니다.

`--replace-reviewed-bot-cue`는 동일 봇의 검토한 회색 안내 문구만 한 작업에 한 번 교체하도록 별도 허용합니다. 일반 앱은 기존 초안을 계속 보호합니다. `--step` 선택 시험은 전체 시험 통과로 집계하지 않습니다.

가상 창 회귀 검사는 82/82를 VM에서 통과했고, WPF smoke는 종료 코드뿐 아니라 새 실행의 `NoticeSender-smoke-success.json` 생성까지 확인했습니다. 앱 자체 D/B 첨부 이후 사라진 다른 창을 UIA로 읽는 오류를 재현했고, 정확한 방 제목을 네이티브 단계에서 먼저 필터링하는 수정의 후속 검증을 진행합니다. 실제 첨부 완료를 읽을 수 있는 근거가 없는 경우 `확인 필요`를 유지합니다.

최종 회귀 검사: 대화 목록의 네이티브 선택자를 스크롤바(id202)에서 실제 대화 목록(id100, 정확한 클래스·직접 부모·PID)으로 수정한 후 VM에서 **87/87 통과**했습니다. 실제 봇 목록의 `WM_GETTEXT`는 길이0, MSAA Value/Description은 S_FALSE/null을 반환했습니다. UIA2/3 및 이 네이티브 경로에서 첨부 완료 근거를 얻지 못했으므로 완료 조건을 낮추지 않았습니다. 화면 확대 후 OCR도 일부 고유 파일명을 틀리게 읽어 완료 판정에 채택하지 않았습니다.
