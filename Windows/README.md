# 공지발송 Windows

Windows 10/11 x64용 C#·WPF 앱입니다. Mac 소스는 기존 위치에 유지되며 Windows 구현은 이 폴더에 있습니다.

## 실행

현재 버전은 `3.1.2-preview.2`입니다. 로컬 Windows VM에서 앱 자체의 실제 봇 발송 시험 7/7과 별도 한글 첨부 시험을 통과했습니다. `NoticeSender-3.1.2-preview.2-Windows-x64.zip`을 일반 폴더에 풀고 `NoticeSender.exe`를 실행합니다. 자체 포함 배포본에는 .NET 런타임이 포함됩니다. 서명되지 않은 개발 배포본이므로 이 PC처럼 Smart App Control이 차단하는 환경에서는 검증용 VM을 사용하고 보호 설정을 유지하세요.

실제 사용자 데이터 없이 화면과 입력을 확인하려면 `NoticeSender.exe --demo`를 실행합니다. 데모 모드는 가상 학생·가상 채팅 연결을 사용하고 실제 카카오톡 메시지를 보내거나 실제 DB를 변경하지 않습니다.

## 주요 흐름

1. 학생 DB에서 CSV·TSV·XLSX를 가져오거나 직접 학생을 등록합니다.
2. 반을 만들고 학생과 기본 프리셋을 연결합니다.
3. 수업 및 발송에서 반·날짜·프리셋을 선택하고 직접 공지 또는 일반/모의고사 결과를 입력합니다.
4. 공통 메시지는 최대 5개를 사용하고, 파일이 필요하면 첨부파일 루트 폴더를 선택합니다.
5. 학생별 최종 문구와 첨부파일을 검토하고 먼저 드라이런을 실행합니다.
6. 실제 발송은 대상·문구·파일을 보여주는 확인창을 승인한 뒤에만 시작합니다. 내용이 바뀌면 다시 검토합니다.

첨부파일은 최종 검토 때의 이름·크기·전체 경로와 내용으로 고정합니다. 승인 후 파일이 바뀌거나 없어지면 첫 메시지 전에 전체 작업을 중단합니다. 닫힌 채팅방은 앱이 열고 정확한 창과 입력란을 다시 확인합니다.

일반 발송에서 카카오톡의 첨부 완료 정보를 읽지 못하면 `첨부 전송 확인` 창이 표시됩니다. 카카오톡에서 표시한 파일이 모두 전송된 것을 직접 확인한 뒤 체크하고 진행하세요. 이 경우 발송 기록의 완료 확인 방식은 `사용자 확인`이며 자동 확인과 구별됩니다. 확인하지 못하거나 취소하면 `확인 필요`로 중단하고 다시 보내지 않습니다.

완료 또는 확인 필요 항목은 같은 발송 회차에서 다시 보내지 않습니다. 다음 수업 등에서 동일한 문구를 의도적으로 다시 보내려면 `새 발송 회차`를 눌러 새 회차를 확인한 뒤 최종 검토를 진행하세요. 이전 수업이나 되돌리기로 이전 회차를 복원하면 그 회차의 중복 발송 보호가 유지됩니다.

Mac용 학생 CSV, 전체 JSON 백업, 반 및 프리셋 JSON과 호환되도록 UUID·camelCase 필드·한국어 상태값을 유지합니다. 플랫폼마다 파일 경로가 다르므로 가져온 첨부파일 루트는 Windows 폴더로 다시 선택하세요. Apple Intelligence 문구 편집은 macOS 전용이므로 Windows에서는 일반 프리셋 편집기를 사용합니다.

## 카카오톡과 드라이런

Windows용 카카오톡을 실행하고 로그인합니다. 실행 계정과 권한 수준이 같아야 합니다. 방 제목과 입력창을 접근성 API 또는 카카오톡 소유의 자식 창으로 정확히 특정할 수 없으면 발송을 차단합니다. 비슷한 방 이름, 중복된 제목, 현재 포커스, 좌표 또는 OCR 추측으로 대상을 대체하지 않습니다.

시작 / 진단 화면의 `방 열기 드라이런`에서 정확한 방 이름을 한 줄에 하나씩 입력할 수 있습니다. 앱이 순서대로 방을 열고, 기존 창 확인과 새로 열기를 구분해 결과를 기록합니다. 이 전용 창은 학생 DB를 열거나 변경하지 않으며 메시지·파일 전송 기능에 접근하지 않습니다. 데모 모드에서는 이 실제 카카오톡 연결 버튼도 비활성화됩니다.

드라이런은 채팅방 검색과 열기·확인만 수행합니다. 방 이름은 메인 창의 검색란에만 입력하고 열기 명령은 검색 결과 목록에만 보냅니다. 메시지 입력란의 변경·전송 키 입력·첨부파일 붙여넣기·파일 전송은 하지 않습니다. 실제 발송 도중 오류나 중지가 발생해 일부 전달 가능성이 있으면 `확인 필요`로 기록하고 자동 재전송하지 않습니다. 파일의 전송 완료를 확인하지 못한 경우에도 중지하며 서버의 최종 수신까지 보장하지 않습니다.

실제 사용 전 연결 진단과 대상별 드라이런이 필요합니다. 카카오톡 버전 또는 화면의 접근성 정보가 달라지면 정확한 대상 식별을 보장할 수 없어 안전하게 중지할 수 있습니다.

현재 로컬 카카오톡의 검색 결과는 접근성 이름을 제공하지 않습니다. 방 열기 전용 드라이런은 메인 창에 속한 검색란·결과 목록을 별도로 특정하며, 검색 결과 갱신 지연에는 같은 결과 목록의 열기 확인만 제한적으로 반복합니다. 실제 앱에서 상위 5개 방 열기 드라이런이 모두 통과했습니다. 알림 전용 방은 열기 성공과 발송 불가를 구분해 `CanCompose=false`로 기록합니다. 이 결과를 실제 발송 허가로 재사용하지 않으며 실제 발송은 고유한 입력창과 원문·소유권을 다시 검사합니다.

호스트 보호를 유지한 별도 로컬 Windows VM에서 2026-11-04 08:53 KST의 전체 봇 시험이 7/7 통과했습니다. 개별·공통 텍스트, TXT/CSV 단일·다중·첨부 단독, PDF, PNG와 첫 메시지 뒤 중단·재전송 차단을 앱이 실행했습니다. 봇 시험은 고유한 합성 파일과 정확한 대화 내용 창의 연속 화면으로 자동 완료를 확인하며, 사용자 확인을 시험 통과로 사용할 수 없습니다. 반복되는 일반 파일명은 과거 첨부와 구별하기 어려워 이 자동 판정을 재사용하지 않습니다. 실제 학생·지인에게는 시험 발송하지 않았습니다. 상세 범위는 [검증 기록](TESTING.md)을 참고하세요.

Windows에는 Mac의 손쉬운 사용 승인과 동일한 공지발송용 권한 토글이 없습니다. 일반 카카오톡은 같은 Windows 사용자·권한 수준에서 제어하고, 실행 신뢰 정책 차단과 제어 권한 문제는 구분해야 합니다. Smart App Control에는 앱별 한 번 허용 기능이 없습니다. 관리자 권한으로 다시 실행하거나 `uiAccess`를 켜는 것으로 이 문제를 해결할 수 있다고 안내하지 않습니다. [Microsoft FAQ](https://support.microsoft.com/en-us/windows/security/threat-malware-protection/smart-app-control-frequently-asked-questions)

## 개발

Windows와 .NET 10 SDK가 필요합니다.

첨부 완료 확인 시험을 포함하는 배포는 [OCR 구성 안내](OCR-RUNTIME.md)에 따라 검토한 로컬 런타임을 함께 패키징합니다.

현재 PC의 보호 설정을 유지하는 [신뢰 서명 준비 및 검증 절차](SIGNING.md)를 별도로 마련했습니다. SignPath 심사 신청 후 실제 서명은 대기 중이며, VM 시험 통과가 호스트의 실행 신뢰를 부여하지는 않습니다.

```powershell
./scripts/build-windows.ps1
./scripts/build-windows.ps1 -Publish
```

자동 테스트는 가상 채팅 연결을 사용합니다. `--smoke-test`도 실제 DB를 열거나 메시지를 보내지 않고 데모 창의 시작과 기본 구성을 검증합니다. 자동 테스트나 CI에 실사용 학생 데이터·카카오톡 대화·백업 파일을 포함하지 마세요.

자동화된 방 열기 시험은 `NoticeSender.exe --dry-run-rooms rooms.json --report result.json --exit-after-dry-run`으로도 실행할 수 있습니다. `rooms.json`은 정확한 방 이름의 JSON 배열이며 이 경로도 실제 DB를 사용하지 않습니다. 방 이름과 결과 파일은 개인정보로 취급해 저장소에 올리지 마세요.

REA로 원본의 공식 Mac 배포 ZIP v3.0.10의 컨테이너 구조를 정적으로 확인했으며, 실제 이식 기준은 더 최신인 저장소 커밋 `c652f09`(앱 3.0.26)의 공개 소스입니다. ZIP 분석은 앱 실행 또는 내부 런타임 동작 검증을 의미하지 않습니다.
