# Windows automation safety and compatibility

The adapter enumerates native top-level HWNDs owned by `KakaoTalk.exe`, then binds UI Automation to those handles. Custom top-level controls do not have to expose the UIA Window role. It targets a unique exact native room title. Each write rechecks PID, HWND, room identity, unique writable composer and child ownership. Before sending, targeted UIA focus lets KakaoTalk remove its own cue; the adapter then reads the native control and blocks any remaining draft, without clearing or special-casing its contents. Text is read back before sending with an owned semantic Send button or targeted HWND Enter; it never types into the currently focused window.

Resolution can set an accessibility-labelled search edit and invoke one exact unique result. If KakaoTalk hides either control, open the intended room manually. Dry run only resolves/opens rooms; it never calls message entry, attachment selection, Enter, or completion.

Attachments follow the individual message and all common messages. They require either an accessible file button with a fully verified owned file-selection dialog, or a unique native HWND registered to accept file drops. The native fallback posts an immutable Unicode HDROP directly to that owned window, without a clipboard or focus dependency. Single and multiple paths are supported. Any confirmation must name every selected file and expose an owned semantic Send button. Success requires increased filename evidence inside an accessible transcript container (or owned native transcript control 202) for every selected file, no owned dialog, and no progress indicator. Duplicate basenames are refused because completion cannot be distinguished. Unsupported KakaoTalk accessibility layouts stop safely; they are not treated as successful sends.

`전송 요청 완료` describes an accepted send request, not server-side receipt or read confirmation. An operation interrupted after any transport write begins becomes `확인 필요`; subsequent runs skip it. A durable `전송 중` log also prevents automatic retry after a crash. The coordinator freezes reviewed message/path values before awaiting UI work, serializes runs, persists before transport access, and stops the batch on ambiguity or any failure.

The console tests use synthetic data and fake transports. Native guard tests use an impossible PID, a nonexistent temporary filename, or an already-cancelled token and never contact a real room. Run them using `dotnet run --project Windows/NoticeSender.Automation.Tests`.

Read-only `--live-inspect` reports process/session identity, native handles and titles, UIA roles and IDs, writable composer capability, registered drop handles, and targeted text lengths without printing message contents. Explicit live diagnostics use `--live-dry-run --room EXACT`; this does not send text or files. Actual delivery is available only with `--live-bot-smoke --room EXACT --acknowledge-bot-only`, with a strict allowlist of 카카오톡 선물하기, 지모, and KREAM. It sends synthetic notices and temporary test files, checks protected-item retry exclusion, stops after any incomplete item, and writes a JSON report under `outputs/`. These modes are never run by the default test suite.

Live diagnostics need access to the interactive Windows desktop. A restricted execution environment may list the KakaoTalk process while hiding its HWNDs or denying native enumeration. Compare inspection reports from the authorized desktop context before treating this as an application compatibility failure; the adapter never retries or changes recipients to bypass such a failure.
