# Windows automation safety and compatibility

The adapter enumerates native top-level HWNDs owned by `KakaoTalk.exe`, then binds UI Automation to those handles. Custom top-level controls do not have to expose the UIA Window role. It targets a unique exact native room title. Each write rechecks PID, HWND, room identity, unique writable composer and child ownership. Before message entry or file attachment, it restores a minimized validated room, requests foreground once, focuses the exact composer through UIA, and requires both native thread active/focus handles and fresh UIA keyboard-focus evidence. It then waits up to one second for KakaoTalk to clear its own cue and blocks any remaining draft, without clearing or special-casing contents. Lost focus blocks further writes; denied activation and focus/preflight errors include handle/state and text-length diagnostics without contents. Text is read back before sending with an owned semantic Send button or targeted HWND Enter; it never types into the currently focused window.

Actual-send resolution can set an accessibility-labelled search edit and invoke one exact unique named result. It fails closed when that exact accessible result cannot be established. `IDryRunChatClient.OpenRoomDryRunAsync` is a separate opening-only path used by coordinator dry runs. It identifies the unlocked active native main window, OnlineMainView, ChatRoomListView, unnamed Edit 100 and SearchListCtrl 1003 by process, class, control ID, native name and direct ancestry. Only that search edit receives the room query; readback and ownership checks precede queued Enter to the visible, enabled owned result list. No composer text, composer Enter, file selection, message delivery or completion method is invoked. A successful standalone opening requires one exact verified native room root and reports whether it was already open. Notification-only rooms may return ComposerHandle 0 and CanCompose false; multiple composer candidates still fail. Normal lesson dry runs reject that read-only capability explicitly, and every actual send still requires the unique owned nonzero composer.

The shared search operation holds a per-user session named mutex for its full duration in both strict resolution and dry-run opening. A second app window or process fails before desktop access while that lease is held. Cancellation, changed query, changed ownership, duplicate controls, a locked main window or an inactive chat view stop safely.

It stops immediately when the exact room appears, and still requires final unique room/composer verification. This never retries delivery. Owned windows are not inherently modal. Read-only native diagnostics and the app's captured image identified the gift channel's visible WISH:NOW menu as an enabled-owner modeless pane with no UIA WindowPattern. Preflight now blocks visible owned standard dialogs, explicit UIA modals, and disabled-owner popups. Attachment discovery excludes its initial visible-owned-window baseline even if a later modal disables the owner, while newly visible owned windows remain subject to PID/ownership checks and ambiguity refusal. No policy setting was changed.

Semantic actions and file-name edits additionally require a nonzero native control HWND with matching UIA/native PID and a native child relationship to the exact expected room or file dialog. Patterns are resolved first; scope is revalidated before the final composer-text guard or dialog mutation. Virtual search results with no verifiable HWND fail closed. The native composer, search-list and file-drop routes retain their explicit HWND checks. Five newly authored scope regressions are **unexecuted** because of the confirmed Smart App Control block; compile success is not a passing test result.

Attachments follow the individual message and all common messages. They require either an accessible file button with a fully verified owned file-selection dialog, or a unique native HWND registered to accept file drops. The native fallback posts an immutable Unicode HDROP directly to that owned window, without a clipboard or focus dependency. Single and multiple paths are supported. Any confirmation must name every selected file and expose an owned semantic Send button. Success requires increased filename evidence inside an accessible transcript container (or owned native transcript control 202) for every selected file, no owned dialog, and no progress indicator. Duplicate basenames are refused because completion cannot be distinguished. Unsupported KakaoTalk accessibility layouts stop safely; they are not treated as successful sends.

`전송 요청 완료` describes an accepted send request, not server-side receipt or read confirmation. An operation interrupted after any transport write begins becomes `확인 필요`; subsequent runs skip it. A durable `전송 중` log also prevents automatic retry after a crash. The coordinator freezes reviewed message/path values before awaiting UI work, serializes runs, persists before transport access, and stops the batch on ambiguity or any failure.

The console tests use synthetic data, fake transports and test-owned native windows. Native search regressions exercise real unnamed edits, view ancestry, visible result lists, decoy edits, preserved drafts, cancellation and queued messages without contacting a real room. A child-process mutex test verifies cross-process contention before desktop access. Run them using `dotnet run --project Windows/NoticeSender.Automation.Tests`.

Read-only `--live-inspect` reports process/session identity, native handles and titles, UIA roles and IDs, writable composer capability, registered drop handles, and targeted text lengths without printing message contents. Explicit live diagnostics use `--live-dry-run --room EXACT`; this does not send text or files. Actual delivery is available only with `--live-bot-smoke --room EXACT --acknowledge-bot-only`, with a strict allowlist of 카카오톡 선물하기, 지모, and KREAM. It sends synthetic notices and temporary test files, checks protected-item retry exclusion, stops after any incomplete item, and writes a JSON report under `outputs/`. These modes are never run by the default test suite.

Live diagnostics need access to the interactive Windows desktop. A restricted execution environment may list the KakaoTalk process while hiding its HWNDs or denying native enumeration. Compare inspection reports from the authorized desktop context before treating this as an application compatibility failure; the adapter never retries or changes recipients to bypass such a failure.
